# Catalog dedupe — dry-run proposal (2026-08-13)

Read-only audit of prod. **Nothing has been written.** Apply step is gated behind `-v apply=1`.

## Verdict

| Group | Finding | Action |
|---|---|---|
| `notes LIKE 'Unknown:%'` (gate31, 1250 rows → 264 products) | Genuine duplicates. 986 redundant rows, zero references from real user data. | **Dedupe** — hide + clear embedding |
| `notes IS NULL` (288 rows → 253 URLs) | **Not** duplicates. The URL collisions are bad URLs on distinct products. | **Leave alone** |

## Are the gate31 duplicates wanted? No.

Checked across all 264 groups, the members are byte-identical:

```
name_differs | image_differs | embedding_differs | price_differs | description_differs | type_differs | size_differs | groups
           0 |             0 |                 0 |             0 |                   0 |            0 |            0 |    264
```

Only `source_sku` and `url` differ (the `?variant_id=` in the affiliate deeplink). Decisively:
**`size_type` is empty on all 1250 rows** (`count(DISTINCT size_type) = 0`). The size distinction
exists only inside the affiliate URL — no column carries it, no UI reads it, no query filters on it.
So the extra rows buy nothing and cost precision.

### What references them

| Site | Kind | Refs → drop set | Refs → keepers |
|---|---|---|---|
| `outfit_items.wardrobe_item_id` | only real FK to `wardrobe_items` | **0** | 0 |
| `user_likes` | via `outfit_id`, and no outfit holds a gate31 item | **0** | 0 |
| `user_looks.items` jsonb (`type: "basic"`) | real user data | **0** | 8 |
| `user_item_dislikes` | user pref | **0** | 1 |
| `wardrobe_items.basic_item_id` | self-FK | 0 | 0 |
| `usage_events` / `widget_events` / `widget_reco_cache` / `user_fittings` | — | 0 | 0 (last three: table empty) |
| `recommendation_logs` | append-only impression/click history | 106,308 | — |
| `main_recommendations.look_sections` jsonb | daily rec cache, regenerated by cron | 20,818 | — |

The zeros in the first five rows are not luck — the keeper is chosen as *"the id already referenced by
user data, else the lowest id"*. With today's data that rule promotes all 9 referenced ids to keepers,
so **no FK and no jsonb blob needs re-pointing.** Verified: the plan's SQL derivation reproduces the
986-id set computed independently via `decode_merchant_url()` exactly.

`user_looks` ids were checked for id-space collision with `wardrobe_user_items` (which also appears in
that jsonb as `type: "user"`) — no overlap: `wardrobe_user_items.id` maxes at 1589, gate31 ids start at 2503.

### The embeddings are the actual damage

All 1250 gate31 rows carry an embedding, and `_auto_build_index` ([main.py:80](ai-service/main.py:80))
loads every row `WHERE embedding IS NOT NULL` with **no `is_hidden` filter and no product dedupe**.
So FAISS holds 1250 vectors for 264 products — `/clip/search` and `/clip/search/text` return the same
garment six times over. gate31 is 22% of the index for 5% of the products.

**This is why `is_hidden = true` alone is not enough** — hidden rows stay in the index.

## Proposal

One statement, no deletes:

```sql
UPDATE wardrobe_items SET is_hidden = true, embedding = NULL, updated_at = now()
 WHERE id IN (<the 986 derived ids>);   -- derivation + dry run in dedupe_gate31.sql
```

Then restart `modemorph-ai` (or `POST /clip/build-index`) to rebuild: **5767 → 4781 vectors**.

**Why not `DELETE`.** 106k `recommendation_logs` rows point at these ids with no FK, so a delete
wouldn't error — it would silently blank every analytics join over four months of impression history.
Keeping the row costs ~1 KB. Delete later if you decide that history is expendable.

**Reversible both ways.** The apply block snapshots `(id, is_hidden, embedding)` into
`dedupe_gate31_backup` first; and even without it, each cleared vector is recoverable from its
surviving twin, which is byte-identical (rollback query at the bottom of the .sql).

**Not touched:** `recommendation_logs` and `main_recommendations` keep pointing at hidden rows.
The former is append-only history that should stay honest about what was actually served; the latter
is regenerated daily by cron and self-heals.

## Why the NULL-notes group is a different problem

288 rows, 253 URLs — but only 10 groups have >1 row, and **in all 10 the members disagree on both
name and image.** These aren't size variants; the URLs are wrong:

```
lime-shop.com/.../12363_7803_523-cernyi   → id 262 "бралетт на бретелях" + id 264 "сумка из замши"
lime-shop.com/.../24939_0079_743-seryi    → id 284 "Сумка"               + id 326 "Плетеная сумка из замши"
you-wanna.ru/.../770101610rsp24           → id 119 skirt black           + id 121 skirt white
```

Deduping on URL here would delete distinct products. A further 26 rows have no usable URL at all,
so URL can't be the identity key for this group in the first place. **Recommendation: leave it.**
If it's worth cleaning, the fix is correcting the URLs (a manual-entry data-quality task), not merging rows.

## Separate finding (not part of this change)

**1,256 hidden rows are in the FAISS index right now** — `is_hidden` is honoured by
`/clip/outfit`, `/clip/complement` and `/clip/score-outfit`, but not by the two index builders
([main.py:80](ai-service/main.py:80), [routes.py:790](ai-service/clip/routes.py:790)), and
`/clip/search` + `/clip/search/text` return raw FAISS neighbours with no post-filter. So items
hidden by the `pick-flatlay` / kids purges are still served by visual search. Adding
`AND COALESCE(is_hidden, false) = false` to both builders fixes it — say the word and I'll do it.
